AI Coding Agents Generate Broken JSON Constantly — How to Fix It

Refreshed October 26, 2026 — new section on catching bad JSON in CI before it ships.

AI coding agents are everywhere right now. Claude Code, the latest OpenAI Codex updates, OpenCode 2.0, and cheaper coding models like GPT-6.1 Sol have put an agent inside every developer's workflow — and the Model Context Protocol (MCP) ecosystem, built on JSON-RPC, has made JSON the native language those agents speak. Agents now generate JSON constantly: tool calls, config files, API payloads, MCP server manifests, and skills policies. The problem is that AI-generated JSON breaks all the time. This guide covers the six ways agent output goes wrong, a step-by-step fix workflow using the free tools on this site, and prompt tricks that make agents emit valid JSON in the first place.

Why agents break JSON (it's not your fault — almost)

Language models predict text, not syntax. A model can write a flawless 500-line function and still drop a comma in a 12-line config, because it never parses its own output. JSON is unforgiving: one stray character invalidates the entire document, while the model was trained on chatty, forgiving prose. When you pipe agent output straight into JSON.parse, you get runtime explosions at the worst possible moment — usually inside an MCP tool call or a deployment script. The fix is a habit, not a talent: never trust agent-generated JSON. Clean it, validate it, then use it.

The 6 ways agent-generated JSON breaks

1. Truncated output

Models hit token limits. You get a beautiful config that simply stops: the closing braces never arrive because the response was cut off at the model's output limit or your tooling's max_tokens cap. The symptom is Unexpected end of JSON input, and the document ends mid-string or mid-object.

{
  "server": "my-mcp-server",
  "command": "npx",
  "args": ["-y", "mcp-server-fetch"]
// ❌ the file just ends here — no closing braces

The fix is simple: ask the agent to continue from where it stopped, or raise the token limit, then validate the complete document.

2. Trailing commas

Agents copy patterns from JavaScript, where trailing commas are perfectly legal. In strict JSON they are fatal — and this is one of the most common single-character failures in agent configs.

{ "name": "codebase-search", "enabled": true, }  // ❌ trailing comma
{ "name": "codebase-search", "enabled": true }    // ✅ correct

3. Markdown code fences around the JSON

This is the number-one error in agent workflows. You asked for JSON; the agent gave you JSON wrapped in ```json ... ``` fences, because it is a chatbot first and a data emitter second. Pasting that into a parser fails immediately, no matter how perfect the JSON inside is.

```json
{ "model": "gpt-6.1-sol" }
```
// ❌ the fences are not JSON

Strip the fences before anything else — the regex workflow below does this in seconds.

4. Smart quotes and curly punctuation

Some models (or the editor you pasted through) convert straight quotes into curly ones: “key” instead of "key". JSON accepts only ASCII double quotes, so a document that looks perfect in a chat window fails in every parser.

{ “tool”: “web_search” }   // ❌ curly quotes — invalid
{ "tool": "web_search" }   // ✅ straight quotes — valid

5. Comments inside JSON

Agents love to explain themselves inside the payload: // fetch the docs here or /* TODO: fix later */. Standard JSON has no comments at all — that is what JSONC is for, and your parser is not running JSONC.

{
  "endpoint": "https://api.example.com", // ❌ comment — invalid
  "timeout": 30
}

6. Schema drift: the agent changes field names mid-conversation

The nastiest failure of all. In message 1 the agent emits {"tool_name": "shell"}. By message 40 it is emitting {"toolName": "shell"} or nesting the same data one level deeper. Nothing is syntactically wrong, so validators pass — but your code expects one shape and the agent silently changed it. This is especially common with MCP tool definitions and long multi-turn refactors, where the agent "improves" the schema without telling you. The only cure is pinning the shape with a JSON Schema (see below) and re-validating on every generation.

The fix workflow: from broken output to valid JSON in 5 minutes

Step 1 — Strip the code fences with the regex tester

Paste the agent's raw response into our free regex tester. Match the opening fence with a pattern like ^```(json)?\s* and the closing fence with ```$ (multiline mode on), and replace both with an empty string. For a one-shot cleanup of the whole response, use /```(json)?\s*\n?([\s\S]*?)```/ and replace with $2 to keep only the JSON between the fences.

Step 2 — Validate to find the exact error

Paste the cleaned text into our JSON formatter and validator. It reports the precise line and character where parsing fails, with a plain-English explanation. Fix that spot, re-validate, repeat. This beats staring at 400 lines of MCP config trying to spot a missing brace, and it usually takes under a minute per error.

Step 3 — Clean up quotes and stray characters

If the validator flags unexpected characters, hunt them with the regex tester. Smart quotes: find [“”‘’] and replace with a straight " (or ' as appropriate). Stray comments: match //.*$ per line — but be careful with URLs inside string values, which contain // legitimately. Always re-validate after a bulk replace.

Step 4 — Handle encoded payloads

Agents sometimes hand you base64-encoded JSON, which is common in MCP transports and API request bodies. If the output looks like random alphanumeric soup ending in =, paste it into our free base64 decoder, then validate the decoded text with the JSON formatter.

Step 5 — Minify for production

Once the document validates, hit Minify in the JSON formatter to produce compact one-line JSON — ideal for config files, environment variables, and request bodies where every byte counts.

A 60-second JSON Schema primer (pin your agent's output)

A JSON Schema is a contract: "this object must have these fields, with these types." Include the schema in your prompt, and validate the agent's output against it before you use it. When output fails, feed the validation error back to the agent — that feedback loop kills schema drift fast, because the model corrects to the contract instead of drifting further.

{
  "type": "object",
  "required": ["tool", "params"],
  "properties": {
    "tool": { "type": "string" },
    "params": { "type": "object" }
  },
  "additionalProperties": false
}

This schema says: an object with exactly two required fields, tool (a string) and params (an object), and nothing else. Give it to your agent, validate every response against it, and field-name drift disappears.

5 prompt tricks that get you valid JSON from agents

  1. Say "raw JSON only." Literally write: "Output raw JSON only — no code fences, no explanations, no comments." Agents obey this surprisingly well when it is explicit.
  2. Show a one-line example. Paste the exact shape you want. Models copy structure far more reliably than they follow prose descriptions of structure.
  3. Demand self-validation. "Validate your output against this schema before answering." The extra reasoning step catches most errors before you ever see them.
  4. Keep payloads small. One tool call per message, not a 60-field manifest. Error rate scales with document length.
  5. Feed errors back verbatim. When it still breaks, paste the validator's exact message into the chat: "Fix this: Unexpected token } at line 14." Concrete error text is the best correction prompt you have.

New: stop validating by hand — put the check in CI

Everything above works, but it still depends on a human pasting output into a validator. The upgrade that pays off fastest is moving the check into your pipeline: add a validation step that runs on every agent-generated config, MCP manifest, or API payload before it is merged or deployed. A simple script that runs JSON.parse (or a schema validator) over every .json file in the change and fails the build on the first error turns a whole class of late-night incidents into a red check on a pull request. Pin the schema in the same repository as the config so the contract and the data change together, and keep a small corpus of known-bad samples — trailing commas, fences, curly quotes, drifted field names — as regression tests. When a new failure mode appears in production, add the sample first, then the fix, so the same break never ships twice.

Two guardrails make this practical. First, prefer structured output modes where your agent platform offers them: a tool-calling or structured-output setting that constrains the model to a declared schema removes most fence and formatting failures at the source, leaving the validator as a backstop rather than the only defence. Second, be sceptical of "auto-repair" steps that silently fix broken JSON by guessing — a repair that inserts a missing brace can also silently change meaning, especially in access-control or billing configs. A safer pattern is: validate, and on failure, return the exact error to the agent for one retry; if the retry still fails, fail loudly and route it to a human. That keeps the feedback loop from the prompt tricks above, but removes the human from the boring middle — the machine does the checking, and people only see the genuinely ambiguous cases.

Frequently asked questions

Why do AI coding agents produce invalid JSON so often?

Language models predict text, not syntax. They do not parse their own output, and JSON is strict — a single stray character invalidates the whole document. The model was trained on chatty, forgiving text, so it adds explanations, code fences, and comments that break parsers. Always validate agent output before piping it into JSON.parse.

How do I strip markdown code fences from agent output?

Paste the agent's response into a free regex tester and match the fences — a pattern like ```(json)? at the start and ``` at the end — replacing them with nothing. Then validate the cleaned text in a JSON formatter to confirm it parses.

What is the fastest way to find the exact line where JSON breaks?

Paste the document into an online JSON validator such as the free DevToolsFree JSON formatter. It reports the exact line and character where parsing fails, in plain English, so you can fix that spot and re-validate instead of scanning hundreds of lines by eye.

How do I make an AI agent output valid JSON reliably?

Tell the agent to output raw JSON only with no code fences or explanations, show it a one-line example of the exact shape, and give it a JSON Schema to conform to. When it still breaks, paste the validator's exact error message back into the chat — error text is the best correction prompt you have.
